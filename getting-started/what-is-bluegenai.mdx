BlueGenAI takes a project from its source requirements through to a running application, and keeps every step traceable back to the requirement that produced it.

## An enterprise approach

**BlueGenAI's approach is the opposite of vibe coding.** Prompting your way to something that runs is no longer the hard part. Producing software an organisation signs off on, maintains, and can be audited against is a different discipline, and it is the one this platform is built for.

That shows up as three commitments, and each is a feature rather than a promise.

| Commitment | How the platform delivers it |
| --- | --- |
| **Traceability** back to well-clarified requirements | Every project starts from a **CAB** — a specification generated from your own documents and source code, which you review and correct |
| **Carefully planned stages** that build interlocked functionality in sequence | Work is broken into **Tickets** and grouped into **Epics**, each Epic a wave in a deliberate build order |
| **Rigorous validation** against well-defined acceptance criteria | Acceptance criteria are written into User Stories, and **App testing** exercises them against the running application |

Those three fit together. The acceptance criteria that get tested are the ones written in the requirement that generated the Ticket, in the Epic that set its place in the build. Nothing in that chain is added afterwards to make the work look organised.

## What you can build

**Web applications**, built end to end: front end, database, and a URL you can hand to a colleague.

**Low-code applications** on Tyler Application Platform, ServiceNow, PowerApps, and Salesforce, where the platform produces the configuration those systems expect.

Both start the same way, with requirements rather than a blank editor.

## How a project runs

1. **Upload what you have.** A solicitation, a requirements pack, an existing codebase, or all three.
2. **Generate a CAB.** The platform reads your material and writes the specification, including a list of what your source material left undecided.
3. **Correct it.** Every change goes through review before it lands.
4. **Generate Tickets.** The corrected specification becomes units of work, grouped into Epics that set the build order.
5. **Prototype, then build.** See it before committing to it, then build the real thing wave by wave.
6. **Test and deploy.** The agent runs your application, tests it against its acceptance criteria, and gives you a URL.

You can join at any step. A team with settled requirements can start at Tickets; a team with only a solicitation starts at step one.
