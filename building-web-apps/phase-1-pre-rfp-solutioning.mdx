Phase 1 — Pre-RFP Solutioning covers all work that happens before development begins. The outputs are primarily visual, narrative, and documentary — prototypes, solution narratives, and procurement documents that either support a competitive bid or build internal alignment before resources are committed.

<Note>
  The Draft Apps generated in the Prototype tab are functional rendered code — not traditional wireframes or static mockups. They are one step away from a fully deployed production application. Switching to the Build tab at any point converts a Draft App into a live deployed application.
</Note>

---

## Why Phase 1 has two paths

Phase 1 serves different purposes depending on your situation. The platform features are the same — the Prototype tab, prompt-driven generation, and procurement document tools. The difference is context, audience, and what the outputs are used for.

|  | Path A | Path B |
| --- | --- | --- |
| **Who** | Contractors and integrators | Government offices and contracted teams |
| **Context** | Pre-award — responding to an RFP or building capture strategy | Post-award — resources are in place, development has not started |
| **Goal** | Win the contract | Align stakeholders and get internal approval before development begins |
| **Outputs** | Client prototypes, proposal artifacts, procurement documents | Leadership review prototypes, concept of operations documents, solution narratives |
| **What comes next** | Award and Phase 2 | Phase 2 — Requirements Refinement & CAB |

## Not sure which path?

If you are responding to a solicitation or building a proposal — **Path A**.

If you already have a contract and need to align stakeholders before development begins — **Path B**.

If you are not sure, start with Path A. The workflow is transferable and the skills carry forward.
